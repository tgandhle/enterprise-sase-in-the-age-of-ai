Part 1: Seeing AI traffic · Module 2

Prompt DLP under TLS inspection

Last reviewed 2026-11-05 · Jump to reference

Objective. After this module you can explain what a secure web gateway can and cannot see in a request to an AI assistant, configure its data loss prevention scan so that common encodings do not hide a secret, decide what happens to a body too large to scan, and say what the inspection bypass list costs you.

Before you start. You should know that HTTPS encrypts a request between the client and the server, and that a gateway can only read the body if it performs TLS inspection. You should be able to read a JSON request body.

1. The attack

Running example: a support engineer at ExampleCorp is chasing a failed payment retry. They paste the service log into ExampleCorp's approved AI assistant, chat.assistant.example, and ask what went wrong. The log line carries a live API key for ExampleCorp's payment partner. Company names are fictional.

Nobody here meant harm. The same paths work for someone who does. ExampleCorp routes all web traffic through a gateway, and each configuration of that gateway catches a different set of these requests:

2. Why it works

A gateway with TLS inspection ends the client's TLS session, reads the request, and opens its own session to the destination. Only then can a DLP scanner look at the body. Four broken assumptions cause most prompt DLP failures:

  • "An approved destination is a safe destination." An allowlist decides where data may go. It says nothing about what the data is. The approved assistant is exactly where staff paste things.
  • "The scanner sees what the assistant sees." Only if it reads the content the way the assistant will. A JSON parser turns e into e before the model reads it, so a pattern run over the raw bytes misses text that arrives perfectly readable. A base64 file is the same story: the assistant decodes it, a raw-byte scan does not.
  • "If the scanner found nothing, there was nothing." Every scanner has a size limit. A body over it was not scanned, and a policy that lets it through has turned "too large to scan" into "allowed".
  • "All traffic to the assistant goes through inspection." Some applications pin their certificate, so they refuse the gateway's certificate and fail to connect when inspected. The usual fix is to put them on a bypass list, and from then on that traffic is encrypted end to end past the gateway.

3. The control

What the gateway decides, in order

  1. Route all web traffic through the gateway. A device that can reach the internet directly has no gateway control at all.
  2. Check the destination. Unknown or unapproved AI destination: block. A host on the bypass list is allowed without inspection, so every entry is a decision someone has to own.
  3. Decrypt the request. Without this step, nothing below can run.
  4. Check the body size against the scan limit. Over it: block, for AI destinations. Never pass a body the scanner has not read.
  5. Decode the content the way the destination will: parse the JSON, take every string value, and decode every attachment the request declares as base64. If the body does not decode, block it.
  6. Run the detectors over the decoded content. A match: block, and show the user a page that says what was found and what to do instead.
  7. Log every block and every bypass, with the user and the destination. The log is what tells you a bypass is being used to move data.

5. What it proves, and what it doesn't

Proves: a request that passed through the gateway, was under the scan limit, decoded cleanly, and matched no detector, did not contain anything those detectors look for, in any encoding the gateway decoded.

Doesn't prove: that the data is safe. A detector finds the patterns it was written for, so a customer's address in free text, a secret in a format nobody wrote a pattern for, or a key split across two prompts can still pass. It proves nothing about traffic on the bypass list, traffic from a device that does not route through the gateway, or anything a user types on a personal phone. And it says nothing about what the assistant does with what it receives: that side is module 24, Data in model context, of API Security in the Age of AI.

The bypass list is a policy, not a technical limit. A pinned app on the bypass list sends its traffic past every inspection step. Removing it from the list does not make it inspectable: the app refuses the gateway's certificate and stops working. The real choice is to block the app and keep staff on the browser, or to allow it uninspected and cover it with an endpoint control. Write down which one you chose, and why.

6. Prove it

A working configuration must block every one of these on an approved AI destination. If any is allowed, the control is broken:

  • A test secret pasted into a prompt as it is.
  • The same secret with every character written as a JSON \u escape.
  • The same secret inside a file attached as base64.
  • The same secret placed just past the scan limit, and a body exactly one byte over the limit with no secret at all.
  • A body that is not valid JSON, sent with a JSON content type.
  • A request to an AI destination that is not on the approved list.

And it must allow a clean prompt. A control that blocks ordinary use gets turned off.

8. Check your understanding

Why does configuration B miss the key written as \u escapes, when it catches the same key pasted plainly?

B runs the pattern over the raw bytes, where each character of the key is six characters of escape. The assistant's JSON parser turns them back into the key before the model reads it. The scan has to read the content the way the destination does.

Configuration C decodes everything correctly. Why does it still let request 5 through?

The body is over the scan limit, and C's policy for an oversized body is to pass it. The decoding never runs. Configuration D blocks what it cannot scan, which is the only one of the four that stops it.

The desktop app keeps breaking under inspection, so a colleague proposes removing it from the bypass list to "force" inspection. What happens?

The app pins its certificate, so it refuses the gateway's certificate and stops connecting. The traffic is not inspected; it simply fails. The real decision is between blocking the app and allowing it uninspected with an endpoint control, and it needs an owner.

Exercises

Change one thing and predict the output

Each exercise edits one place in labs/prompt_dlp_lab.py and asks what the run prints. The answers are the real output of each variant, not a reading of the code, so you can settle any disagreement by running it. The lab compares every result with the one it expects, so each of these edits also makes it exit 1 and list what differed. None of them needs a package.

1. The decoder stops decoding attachments

In texts_in, the scanner decodes a file the request declares as base64. Replace the line that decodes it with one that passes the encoded text through unchanged:

yield value["data"]
Which verdicts in the published transcript change?

Every option, and why
  • B never calls texts_in. It scans the raw bytes, and it already let line 4 through.
  • Correct. C and D now scan the base64 text, which does not contain the key's characters in order, so both flip to allow: nothing found and the lab reports two mismatches. That is the gap check dlp-02 in the Reference layer closes.
  • Line 3 does not change. The \u escapes are decoded by the JSON parser, not by the attachment step you removed.
  • The key is in the body, but only as base64. A pattern matches characters, and base64 changes every one of them.

2. The scan limit is doubled

Change SCAN_LIMIT = 64 * 1024 to SCAN_LIMIT = 128 * 1024.

What happens to line 5?

Every option, and why
  • B and C change too. Once the body is under the limit, every inspecting configuration scans it.
  • B changes as well. The key in this request is written plainly, so a raw-byte scan finds it once it gets to scan at all.
  • Correct. The body is about 76 KB, so it is now scanned, and all three inspecting configurations find the key. The lab reports three mismatches. A bigger limit fixes this request and nothing else: a user with 130 KB of log is back where line 5 started. That is why check dlp-03 in the Reference layer is about what happens over the limit, not about the limit's size.
  • The body is about 76 KB, under the new limit of 131072 bytes.

3. The desktop app comes off the bypass list

Change BYPASS = {PINNED_HOST} to BYPASS = set().

What does line 6 print under B, C and D, and what would really happen?

Every option, and why
  • That is line 6 under A, which never inspects anything. B, C and D now scan the request.
  • Correct. The lab can scan the request because it does not model certificate pinning, so all three inspecting configurations find the key and the lab reports four mismatches, one for A's changed wording.   • The lab prints that, but a real pinned app never gets as far as sending the body. This is the one place the simulation is kinder than the network.
  • The body is ordinary JSON and decodes cleanly.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardRoute outbound traffic through authenticated proxy servers at managed interfaces. NIST SP 800-53 Rev 5.2.0 control SC-7(8) requires this for the traffic and networks the organization defines, and its discussion names web content filtering devices as one of the most common such proxies.
  • StandardPrevent the exfiltration of information, and conduct exfiltration tests at a defined frequency. NIST SP 800-53 Rev 5.2.0 control SC-7(10), parts (a) and (b). Its discussion says prevention applies to both intentional and unintentional exfiltration, and lists data loss and data leakage prevention tools among the techniques.
  • StandardEnforce approved authorizations for information flows between connected systems. NIST SP 800-53 Rev 5.2.0 control AC-4. Its discussion includes limiting transfers between organizations based on data structures and content.
  • BaselineDecrypt and scan every request to an approved AI destination. An allowlist entry is not a reason to skip inspection.
  • BaselineScan the decoded content: JSON string values and every attachment the request declares as base64, at minimum.
  • BaselineBlock a body over the scan limit, and a body that does not decode, when the destination is an AI service.
  • BaselineKeep the bypass list empty for AI destinations. Block an app that pins its certificate unless an owner accepts the gap in writing.
  • OptionAllow a pinned app uninspected, with an endpoint DLP control on the devices that run it and a review date on the bypass entry.
  • OptionCoach instead of block for low-severity matches: show the user what was found and let them confirm, with the decision logged.

Review checklist items

These are collected into the site checklist.

  • Requests to approved AI destinations are decrypted and scanned A destination allowlist decides where data may go. It is not a substitute for looking at what is sent.
  • The scanner reads content the way the destination will JSON escapes and declared base64 attachments are decoded before any detector runs. A body that does not decode is blocked.
  • A body over the scan limit is blocked for AI destinations It is never passed unscanned. The limit is recorded and tested with a body one byte over it.
  • Every AI host on the bypass list has an owner, a reason, a review date and a compensating control A pinned app is blocked, or allowed uninspected with an endpoint control named in the entry.
  • Exfiltration tests run on a schedule against AI destinations They cover each case in section 6 of this lesson, including a clean prompt that must be allowed.
